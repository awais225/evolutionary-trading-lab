PURPOSE OF THIS FILE
--------------------
This file is the LMSArena-side implementation/testing/commit history.

It is deliberately separate from chatgpt.txt:

    chatgpt.txt    = WHAT THE USER / CHATGPT REQUESTED  (requested-change history)
    lmsarena.txt   = WHAT LMSARENA ACTUALLY DID         (implementation history)

Rules for this file:
  * Append a new dated ENTRY per LMSArena iteration. Never rewrite old entries.

    coding workspace; it lives in LMSArena temporary storage and is referenced
    through the EVOLUTIONARY_LAB_DATA_ROOT environment mechanism.

7. EXECUTION, RESPONSE HANDLING AND VERIFICATION (spec §8/§9/§14)
-----------------------------------------------------------------
  * exactly ONE mt5.order_send per submission (market DEAL, price = ask for BUY
    / bid for SELL, real `sl` and `tp` fields, deviation, magic 7770xx, comment)
  * the retcode is interpreted, never assumed: 10009/10010 -> EXECUTED,
    10008 -> PENDING, 10004/10006/10007/10011/10013..10030/10035..10046 ->
    REJECTED, 10012/10031 -> TIMEOUT, anything else -> UNKNOWN. Each maps to a
    human-readable sentence, keeps the raw retcode + broker comment, and only
    genuine rejections are marked safe to retry.
  * after sending, the result is READ BACK from the terminal: position (or
    pending order) + its actual SL/TP; a broker adjustment of SL/TP is reported
    as `sl_tp_verified=false` together with the broker's real values.
  * status labels: POSITION_OPEN -> "ORDER EXECUTED", retcode PLACED or a
    pending order found -> "ORDER ACCEPTED / PENDING" (never labelled executed),
    DONE without any broker object -> "EXECUTED BUT NOT CONFIRMED BY THE
    TERMINAL", timeout -> "RESULT UNKNOWN - TIMEOUT".
  * no fake success anywhere: a success status requires a DONE/PLACED retcode
    AND the broker object found in the terminal; `source` is always reported.

8. DUPLICATE PROTECTION AND NO AUTO-RETRY (spec §10/§11)
--------------------------------------------------------
  * single-flight gate (token + state lock): a second submission while one is
    in flight -> HTTP 409 ORDER_IN_FLIGHT, nothing sent
  * client_order_id (generated once per confirmation): a replay -> HTTP 409
    DUPLICATE_ORDER, nothing sent
  * the confirmation token "PLACE_DEMO_ORDER" is required by the API itself, so
    a stray request cannot place an order
  * there are no retry loops, no sleeps and no background threads in the
    execution path (asserted by an AST-based test); a timeout/connection error
    returns an explicit warning: the order may have reached the broker, verify
    open positions before resubmitting
  * page load / refresh only ever issues GETs: /state and /status (asserted by
    tests that count requests handed to the terminal = 0)

3. RISK PER TRADE (§7-§9)
-------------------------
  * Risk % is configuration: live_testing.risk_pct_default (1.0 % in this
    build) and live_testing.risk_pct_max (2.0 %), editable through
    POST /api/live-testing/settings - never a literal in the code.
  * Risk amount = live MT5 account equity x risk % (equity comes from the V4.2
    account safety block; no hard-coded balance anywhere). Measured against the
    MT5 test double: equity 10 000.00 -> 0.50 % = 50.00 risk.
  * Volume = risk_amount / (stop_distance / trade_tick_size x trade_tick_value),
    floored to the broker volume step and re-checked against min/max - broker
    contract data only, no pip constant, no pip approximation. Measured: node
    514 (BUY XAUUSD, ATR-based stop 2.09, tick size 0.01, tick value 1.0,
    volume min 0.01 / step 0.01) -> 0.23 lots for 50.00 risk.
  * Per-node override wins: live_test_configs.risk_pct is resolved by
    resolve_risk_pct() and reported as risk_pct_source = "node_override" vs
    "global_default".
  * Safety (all blocking, never clamping): risk <= 0 -> RISK_PCT_NOT_POSITIVE;
    risk > maximum -> RISK_PCT_ABOVE_MAXIMUM (the trade is blocked and the
    error is shown, the value is never quietly reduced); missing tick size /
    tick value / volume min-step or a non-tradable symbol ->
    SYMBOL_SPEC_UNAVAILABLE / SYMBOL_NOT_TRADABLE; missing SL -> SL_REQUIRED;
    zero-distance SL -> SL_DISTANCE_ZERO; volume below the broker minimum ->
    VOLUME_BELOW_MINIMUM (refusing to round the trade size up past the
    requested risk).

7. ACTIVATION / DEACTIVATION (§4-§6, §20, §21)
----------------------------------------------
  * Live Testing always comes up INACTIVE: on app/server start, page or browser
    reload, after an MT5 reconnect and after a research-run change. There is no
    persisted active flag; get_mode() exposes previously_active vs the current
    state for display only.
  * Activation is a two-step flow: GET /api/live-testing/confirmation returns
    the panel content (account and DEMO verification, node scope, symbols, risk
    setting, max active trades, market state, demo-order warning) and
    POST activate requires confirmed=true from that panel. A request without
    the explicit confirmation is refused, and activation is refused while
    execution is not allowed (non-demo or unavailable MT5).
  * POST deactivate ("STOP LIVE TESTING") returns the engine to INACTIVE and
    blocks new orders immediately; it never touches open positions.
  * POST stop-new-trades stops new entries while the engine keeps running, and
    POST close-positions is a separate explicit operation (it refuses when no
    real MT5 broker state is available). STOP NEW TRADES and CLOSE EXISTING
    POSITIONS are therefore distinct, and nothing is liquidated automatically
    in this version.
  * A disconnect deactivates the engine with an explicit reason and leaves
    positions untouched; reconnecting does not resume - the operator must
    activate again.

8. STAGE-BY-STAGE LIVE LOG (§14, §15)
-------------------------------------
  * Stages: SIGNAL DETECTED -> RISK CALCULATED -> VOLUME CALCULATED ->
    MARKET VALIDATED -> ORDER VALIDATED -> ORDER SENT -> BROKER RESPONSE ->
    POSITION VERIFIED, plus BLOCKED / REJECTED / UNKNOWN VERIFY MT5 outcomes.
  * Every event carries timestamp, node id, strategy id, run id, symbol, side,
    status, code and a human-readable message; raw MT5 objects stay on the
    server and no [object Object] is ever emitted.
  * Broker timeouts or ambiguous responses are marked UNKNOWN - VERIFY MT5 and
    the symbol is gated: a further attempt on that symbol is BLOCKED with
    UNRESOLVED_BROKER_STATE until the broker state has been verified. Reconcile
    releases the gate only for rows older than the 60 s grace period whose
    positions/orders are gone, keeps the audit row UNKNOWN and emits a VERIFIED
    stage. No automatic retry, no second order on a timeout.
