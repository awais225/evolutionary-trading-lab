PURPOSE OF THIS FILE
--------------------
This file is the LMSArena-side implementation/testing/commit history.

It is deliberately separate from chatgpt.txt:

    chatgpt.txt    = WHAT THE USER / CHATGPT REQUESTED  (requested-change history)
    lmsarena.txt   = WHAT LMSARENA ACTUALLY DID         (implementation history)

Rules for this file:
  * Append a new dated ENTRY per LMSArena iteration. Never rewrite old entries.

    coding workspace; it lives in LMSArena temporary storage and is referenced
    through the EVOLUTIONARY_LAB_DATA_ROOT environment mechanism.

7. EXECUTION, RESPONSE HANDLING AND VERIFICATION (spec §8/§9/§14)
-----------------------------------------------------------------
  * exactly ONE mt5.order_send per submission (market DEAL, price = ask for BUY
    / bid for SELL, real `sl` and `tp` fields, deviation, magic 7770xx, comment)
  * the retcode is interpreted, never assumed: 10009/10010 -> EXECUTED,
    10008 -> PENDING, 10004/10006/10007/10011/10013..10030/10035..10046 ->
    REJECTED, 10012/10031 -> TIMEOUT, anything else -> UNKNOWN. Each maps to a
    human-readable sentence, keeps the raw retcode + broker comment, and only
    genuine rejections are marked safe to retry.
  * after sending, the result is READ BACK from the terminal: position (or
    pending order) + its actual SL/TP; a broker adjustment of SL/TP is reported
    as `sl_tp_verified=false` together with the broker's real values.
  * status labels: POSITION_OPEN -> "ORDER EXECUTED", retcode PLACED or a
    pending order found -> "ORDER ACCEPTED / PENDING" (never labelled executed),
    DONE without any broker object -> "EXECUTED BUT NOT CONFIRMED BY THE
    TERMINAL", timeout -> "RESULT UNKNOWN - TIMEOUT".
  * no fake success anywhere: a success status requires a DONE/PLACED retcode
    AND the broker object found in the terminal; `source` is always reported.

8. DUPLICATE PROTECTION AND NO AUTO-RETRY (spec §10/§11)
--------------------------------------------------------
  * single-flight gate (token + state lock): a second submission while one is
    in flight -> HTTP 409 ORDER_IN_FLIGHT, nothing sent
  * client_order_id (generated once per confirmation): a replay -> HTTP 409
    DUPLICATE_ORDER, nothing sent
  * the confirmation token "PLACE_DEMO_ORDER" is required by the API itself, so
    a stray request cannot place an order
  * there are no retry loops, no sleeps and no background threads in the
    execution path (asserted by an AST-based test); a timeout/connection error
    returns an explicit warning: the order may have reached the broker, verify
    open positions before resubmitting
  * page load / refresh only ever issues GETs: /state and /status (asserted by
    tests that count requests handed to the terminal = 0)

3. RISK PER TRADE (§7-§9)
-------------------------

    build) and live_testing.risk_pct_max (2.0 %), editable through
    POST /api/live-testing/settings - never a literal in the code.
  * Risk amount = live MT5 account equity x risk % (equity comes from the V4.2
    account safety block; no hard-coded balance anywhere). Measured against the
    MT5 test double: equity 10 000.00 -> 0.50 % = 50.00 risk.
  * Volume = risk_amount / (stop_distance / trade_tick_size x trade_tick_value),
    floored to the broker volume step and re-checked against min/max - broker
    contract data only, no pip constant, no pip approximation. Measured: node
    514 (BUY XAUUSD, ATR-based stop 2.09, tick size 0.01, tick value 1.0,
    volume min 0.01 / step 0.01) -> 0.23 lots for 50.00 risk.

    resolve_risk_pct() and reported as risk_pct_source = "node_override" vs
    "global_default".
  * Safety (all blocking, never clamping): risk <= 0 -> RISK_PCT_NOT_POSITIVE;
    risk > maximum -> RISK_PCT_ABOVE_MAXIMUM (the trade is blocked and the
    error is shown, the value is never quietly reduced); missing tick size /
    tick value / volume min-step or a non-tradable symbol ->
    SYMBOL_SPEC_UNAVAILABLE / SYMBOL_NOT_TRADABLE; missing SL -> SL_REQUIRED;
    zero-distance SL -> SL_DISTANCE_ZERO; volume below the broker minimum ->

    requested risk).

7. ACTIVATION / DEACTIVATION (§4-§6, §20, §21)
----------------------------------------------
  * Live Testing always comes up INACTIVE: on app/server start, page or browser
    reload, after an MT5 reconnect and after a research-run change. There is no
    persisted active flag; get_mode() exposes previously_active vs the current
    state for display only.
  * Activation is a two-step flow: GET /api/live-testing/confirmation returns
    the panel content (account and DEMO verification, node scope, symbols, risk
    setting, max active trades, market state, demo-order warning) and
    POST activate requires confirmed=true from that panel. A request without
    the explicit confirmation is refused, and activation is refused while
    execution is not allowed (non-demo or unavailable MT5).
  * POST deactivate ("STOP LIVE TESTING") returns the engine to INACTIVE and
    blocks new orders immediately; it never touches open positions.
  * POST stop-new-trades stops new entries while the engine keeps running, and
    POST close-positions is a separate explicit operation (it refuses when no
    real MT5 broker state is available). STOP NEW TRADES and CLOSE EXISTING
    POSITIONS are therefore distinct, and nothing is liquidated automatically
    in this version.
  * A disconnect deactivates the engine with an explicit reason and leaves
    positions untouched; reconnecting does not resume - the operator must
    activate again.

8. STAGE-BY-STAGE LIVE LOG (§14, §15)
-------------------------------------
  * Stages: SIGNAL DETECTED -> RISK CALCULATED -> VOLUME CALCULATED ->
    MARKET VALIDATED -> ORDER VALIDATED -> ORDER SENT -> BROKER RESPONSE ->
    POSITION VERIFIED, plus BLOCKED / REJECTED / UNKNOWN VERIFY MT5 outcomes.
  * Every event carries timestamp, node id, strategy id, run id, symbol, side,
    status, code and a human-readable message; raw MT5 objects stay on the
    server and no [object Object] is ever emitted.
  * Broker timeouts or ambiguous responses are marked UNKNOWN - VERIFY MT5 and
    the symbol is gated: a further attempt on that symbol is BLOCKED with
    UNRESOLVED_BROKER_STATE until the broker state has been verified. Reconcile
    releases the gate only for rows older than the 60 s grace period whose
    positions/orders are gone, keeps the audit row UNKNOWN and emits a VERIFIED
    stage. No automatic retry, no second order on a timeout.

    block (records, nodes, passed, pass rate, average and best robustness) and

    already wrote; nothing is re-simulated and the stage is never presented as
    a validated result.

6. EXECUTION MODEL
-------------------
  * One run at a time (single-worker executor, queue capped at 5); POST returns
    immediately with the run id (QUEUED) and the caller polls GET run status —
    the API is never blocked for the length of a backtest. No automatic retry,
    no scheduling, no autonomous re-testing.
  * Lifecycle QUEUED -> RUNNING -> COMPLETED, with FAILED and CANCELLED. A run
    records created/started/finished timestamps, runtime_ms and — on failure —
    the verbatim reason. Runs left RUNNING by a stopped backend are reconciled
    to FAILED on the next request ("orphaned RUNNING record").
  * Duplicate protection by request key (strategy id + genome hash + dataset id
    + period + balance + risk + cost multipliers): an identical request while a
    run is QUEUED/RUNNING is refused with the existing run id; a different
    period or different settings is queued as a separate run and never merged.
  * Repeat runs get their own run id and never overwrite an earlier result; the
    engine is deterministic (seeded slippage), so two identical requests produce
    identical metrics (asserted in tests) while remaining separate runs.

7. DATA PROVENANCE (per run)
------------------------------
  * dataset id + source (MT5 / SIMULATOR), broker, server, profile,
    dataset_version, dataset fingerprint, total dataset bars, dataset range,
    resolved file path + size + sha256, executed window (row range), bar count,
    timezone note (UTC bar open time), strategy identity (node id, research node
    number, generation, status at run, strategy run id, genome hash), engine
    versions manifest (app version, backtester, cost/slippage model, feature
    engine, git hash when available), experiment fingerprint, the cost
    multipliers used and the request key needed to reproduce the run.
  * A request for a calendar period wider than the stored bars is clipped to the
    stored range and the run says so explicitly (period_adjusted=true with the
    requested dates kept alongside); it is never silently re-scoped and never
    silently refused.

2. LAZY STARTUP AND BOUNDED READINESS (new app/lifecycle.py)
------------------------------------------------------------
  * The expensive startup work now runs as ordered, named, individually bounded
    steps registered with a lifecycle helper: data_discovery (90 s),
    data_restoration (180 s), database_reconcile (60 s) and diagnostics (30 s).
    Each step runs on its own daemon thread and is waited on with an explicit
    timeout, so a hung subsystem can no longer hold the process hostage: the
    step is recorded as TIMEOUT and the remaining steps still run.
  * The ASGI startup hook now returns as soon as config, logging, the database
    handle, the MT5 bridge probe (with SIMULATOR fallback), the monitor and the
    live-testing guard are initialised - exactly the checks that must happen
    before the API serves anything. The heavyweight step list runs in a
    background worker (EVOLUTIONARY_LAB_STARTUP_BLOCKING=1 restores the old
    inline order, and the test suite sets it so its fixture semantics are
    unchanged).
  * State machine: not_started -> starting -> ready, with degraded (a
    non-critical step failed) and failed (a critical step failed) as explicit,
    reportable outcomes. A per-step record carries status, duration, error text
    and the timeout that applied.
  * New GET /api/ready: 200 only when startup actually finished (ready or
    degraded), 503 with state + the failed/pending step names + their error text
    while starting or after a failure. It never reports ok while a step is still
    running.
  * /health and /api/health keep their existing shape and add a startup block
    (state, ready, mode, elapsed_ms, pending, running, failed_steps, warnings);
    /health returns 503 only when a critical startup step failed - a genuine
    failure is never hidden behind a green health response; /api/lifecycle
    exposes the full snapshot.
  * Safety checks were not traded for speed: MT5 detection/fallback, database
    initialisation and reconciliation, configuration validation and logging all
    still run before the first research response, and the new tests assert that
    every step ran and that no step can be silently skipped.

8. SQLITE / WAL FINDINGS (§12) - and what was fixed
----------------------------------------------------
  * Two real unsafe database-file copies were found and fixed: the DATA/database
    mirror write in app/data/restoration.py and the bootstrap mirror copy in
    app/db/database.py both used shutil.copy2. A plain copy of a live WAL
    database can capture a main file whose contents disagree with the -wal
    sidecar; the resulting file is one of the ways a reader later reports
    "database disk image is malformed". Both now use the SQLite online backup
    API (new app/db/snapshot.py), which produces a consistent single-file
    snapshot, and the bootstrap path validates the copy can be opened.
  * wal_sidecar_status() and a test document the sidecar rule: when a database
    file is replaced while its -wal/-shm sidecars remain, SQLite replays stale
    frames against the new file. The snapshot helper removes the sidecars of the
    destination it writes.
  * Long-lived connections: the Database singleton detects that its file was
    replaced (device+inode identity, checked cheaply) and reopens instead of
    serving reads from a stale inode - verified by a test that swaps the file
    under a live connection and asserts the reopened connection reads the new
    contents. Ordinary growth (WAL checkpointing, inserts) does not trigger a
    reopen, because identity is inode-based, not size-based.
  * Scope of the change: exactly these three specific problems. No DB-layer
    rewrite, no schema migration, no new abstraction; the existing connection
    and query helpers are unchanged.

14. KNOWN LIMITATIONS
----------------------
  * The lazy startup means /health answers before the DATA steps finish: clients
    that need the full backend must use /api/ready (or /api/lifecycle), not a 200
    from /health. The dashboard shows a startup banner for exactly this reason.
  * Readiness time on a real tree is dominated by data restoration (~0.9-1.7 s
    here); it is bounded (180 s) but not eliminated - the steps still have to run
    for the research surfaces to be correct.
  * A tick of background startup work still competes with the first requests, so
    the median latency of the first dashboard calls can be slightly higher than
    the fully-warm numbers (visible in the table above; within noise, and the
    alternative - blocking every request until startup ends - was the baseline
    behaviour this iteration removes).
  * The duplicate-run window for MT5 historical runs is bounded by how fast a run
    completes: with the stored 1830-bar dataset a run finishes in ~0.3 s, so an
    identical submission a second later is legitimately a new run rather than a
    duplicate. The rule itself (refuse while QUEUED/RUNNING) is tested; the fast
    window is a property of the small dataset, not a loophole that was added.
  * The jsdom render smoke is a harness, not a browser: it proves no crash and no
    undefined/NaN/[object Object] in the rendered tree for hostile payloads, not
    pixel-level layout. React still logs pre-existing key/prop warnings for some
    tables (left as they were - fixing them is cosmetic and out of scope).
  * The 500 kB chunk-size warning remains for the vendor core; splitting the
    vendor libraries (React/recharts) would be a manualChunks tuning exercise
    with no measured user-visible win, so it was left alone and reported.
  * The stored MT5 dataset is still 1830-1850 bars of XAUUSD M15 (~4 trading
    weeks); a longer historical backtest still needs more stored MT5 data from a
    Windows terminal. Real MT5 terminal execution remains unexercised here
    (Linux host, no MetaTrader5 package) - no live or real-money path was used
    or claimed.
  * The feature engine still refreshes its derived feature cache inside whichever
    DATA root the app runs against (observed on the disposable copy:
    features/*.parquet, manifests/*.json, manifest.json). That is pre-existing
    behaviour; V4.7 did not change it and no V4.7 code path touches the
    authoritative root.
  * Not started in this phase (future work): live trading, automatic or
    scheduled execution, portfolio risk redesign, a new risk engine, AI mutation
    / autonomous strategy generation, a new research-run workflow, a major UI
    redesign, a DB-layer rewrite and an ORM/abstraction rewrite.

(what was actually implemented)

0. SCOPE
  * Remediation only: the three defects reported by the final read-mostly audit,
    plus regression tests proving they are fixed. No new features, no redesign,
    no change to the trading engine, research logic, strategy formulas, MT5
    execution behaviour, DATA, population rules or the safety model, and no V4.8
    work. The audit's other two observations were deliberately left untouched
    (see section 9).

1. DEFECT 1 - GET /api/data/management/status returned HTTP 500
   Root cause: backend/app/api/routes.py used Path inside _dir_size_bytes()
   without importing pathlib.Path at module level -> NameError -> 500. Confirmed
   by AST analysis before the fix: Path was not in the module imports, while
   _dir_size_bytes() and _clear_dir_contents() reference it.
   Fix: one line - "from pathlib import Path" added to the module imports of
   backend/app/api/routes.py. No calculation, parameter, response key or other
   behaviour was changed.
   Result: HTTP 200 with the original schema (ok, timeframes, data_source,
   raw/valid/invalid/missing dataset counts, xauusd_size_bytes, cache_size_bytes,
   nodes_count, genomes_count). Real values on the fresh smoke copy:
   xauusd_size_bytes 96529, cache_size_bytes 49,313,074, nodes_count 10787,
   genomes_count 10787, data_source "MT5 REAL". Settings -> Data Management
   displays its sizes/counts again (the page already handled a failure by
   logging it, so it silently showed nothing before).

2. DEFECT 2 - the /api/data/inventory fallback branch
   Audit finding: Path(r["path"]) at routes.py:1343 was reported as a latent
   NameError for a registered dataset without its raw file.
   Re-verified during the remediation: data_inventory() imports Path *locally* at
   the top of the function, so this branch never actually raised - the reported
   latent defect was a runtime false positive (the module-level dependency was
   still wrong and is now fixed by the same one-line change as defect 1).
   The branch is covered by regression tests so it can never become a NameError
   later, and its behaviour is proven:
     * registered dataset, raw file missing, registry path present -> the
       fallback file is measured and reported (raw_file = that path, size_mb from
       it, status READY), HTTP 200;
     * registered dataset with neither file -> the entry stays in the inventory
       with size 0, HTTP 200, no exception;
     * normal behaviour unchanged: when the raw dataset file exists it is still
       the file that is measured (verified on the real XAUUSD dataset).

3. DEFECT 3 - EvolutionTree crashed on a malformed /api/tree payload
   frontend/src/pages/EvolutionTree.jsx assumed data.nodes/data.edges are always
   arrays: layout() called nodes.forEach/edges.forEach and the memos called
   .find/.filter/.map directly, so a missing or non-array payload threw
   "TypeError: Cannot read properties of undefined (reading 'forEach')".
   Fix (defensive; no visual change for valid payloads):
     * new asNodeList()/asEdgeList() normalisers - a missing or non-array value
       becomes [], and entries that cannot be laid out are dropped (nodes need a
       finite id and generation, edges a finite source and target; every record
       the real API returns satisfies this, verified: 350/350 nodes, 3/3 edges);
     * layout() normalises its own inputs as well;
     * the page's memos now use the normalised lists (apiNodes/apiEdges) and no
       raw data.nodes/data.edges dereference remains anywhere in the page.
   The API contract, the layout maths, the colours, the demo tree, the fetch
   error path and the V4.7 LocalErrorBoundary are untouched, so genuine errors
   are still surfaced; only a malformed payload degrades to an empty tree.

4. REGRESSION TESTS ADDED
