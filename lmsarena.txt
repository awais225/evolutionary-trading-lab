This file is the LMSArena-side implementation/testing/commit history.

    lmsarena.txt   = WHAT LMSARENA ACTUALLY DID         (implementation history)

8. FINDINGS AND KNOWN ISSUES (recorded, not silently fixed)
-----------------------------------------------------------
  a) Engine vs legacy (fixed in V4.1): the population cap used a database-wide
     active count, so a routine engine run retired legacy SURVIVED nodes
     (42 rows) and would keep doing so. The cap/clear_failed/reset_generation
     are now scoped away from the legacy population and the acceptance run
     proves the legacy fingerprint is identical from startup to the end of a
     full A/B/C cycle.
  b) DATA-root override hazard (fixed in V4.1): when a run persists absolute
     /.../DATA/... paths into CONFIG/lab_config.yaml, an app started later with
     EVOLUTIONARY_LAB_DATA_ROOT set to a different tree silently opened the
     production database - the absolute path was not under <root>/DATA so the
     resolver returned it untouched. The override is now authoritative for
     persisted DATA-tree paths (and only when it is set explicitly). This was
     found because two verification attempts initially hit the real DATA; the
     data was restored from the pristine copy each time and verified with the
     manifest, no research data was lost.
  c) Still unscoped (pre-existing, unchanged): POST /api/tasks/reconcile and
     restoration.py bulk-update statuses without a legacy filter. The shipped
     DATA has no legacy rows in the affected states (BORN/BACKTESTING/
     VALIDATING), so nothing is damaged today; do not run reconcile against a
     database where legacy rows sit in those states.
  d) try_insert falls back to run_id "RUN-20260927-CLEAN-MT5" and the
     LEGACY_TEST label when no active run is bound. The app binds the run at
     startup, so this only shows up in out-of-band engine processes (it was
     observed while building the verification harness and is why the harness
     binds the run through lab.resume()).
  e) Option B raises the target relative to the ACTIVE run's node count
     (existing machinery). In a clean single-run study that equals the
     population (10000+1000 -> 11000 as verified); after a fresh run has just
     been created the active run is the new one, which is the intended
     "resume the current study" semantic.
  f) Restore replaces rows by id (INSERT OR REPLACE) inside one transaction;
     the legacy strategy rows are never in the restore source, so they are
     never replaced.
  g) App startup touches updated_at on some legacy rows (pre-existing, benign;
     status/generation/hash/fitness are untouched - verified row by row).
