HERO1 TROUBLESHOOTING - SEARCH THIS FILE FIRST

HOW TO USE THIS FILE
--------------------
1. When something fails, Hero1 prints a STAGE number and exact error text.
   Keep that window open (it is designed to stay open).
2. In this file, press Ctrl+F and search for, in this order:
     - the stage text, e.g.  STAGE 4
     - the exact error words on screen, e.g.  file is not a database
     - the port number, e.g.  8788
3. Every entry has four parts:
     SYMPTOM:         what you see, in the exact words shown on screen
     Verified cause:  what was PROVEN to cause it in this project
     Verified fix:    the fix that was verified to work
     Source:          where that verification is recorded
   There are no guessed fixes in this file. If the words on your screen do
   not appear here, do NOT experiment: run START_DIAGNOSTIC.bat, then report
   the stage number, the exact error text, and the two log files
   <DATA_ROOT>\LOGS\startup.log and <DATA_ROOT>\LOGS\diagnostic.log.
   Never delete the DATA folder to "fix" a problem. No fix in this file
   requires deleting data.

Honesty note: the Windows launchers cannot be executed by the development
environment, so they are verified by a static audit plus automated tests
(scripts/audit_launcher.py, tests/test_launcher_bat.py) and are built to stay
open and name the failed stage. If a launcher window still vanishes, the
file being double-clicked is not the current file - see the first entry.

SYMPTOM: The START.bat window closes or vanishes and there is nothing to read
Verified cause: A single-file launcher can die before it reaches any pause
  (a missing label, a parse error or a native crash kills the console), and
  on the affected machine the file being run could not be proven to be the
  file that had been fixed - an old or partial copy looks identical.
Verified fix: The current design cannot vanish: START.bat stays open, prints
  its own absolute path, size, modified time, its SHA-256 (certutil) and the
  git HEAD, then runs the real procedure inside cmd /k. Compare the printed
  SHA-256 with the START.bat in your pulled repository; a mismatch means the
  file you double-clicked is not current - pull again. For diagnosis run
  START_DIAGNOSTIC.bat, which always pauses and writes diagnostic.log.
Source: ISSUE-037, commit a7d435b27; scripts/audit_launcher.py

SYMPTOM: HERO1 STARTUP FAILED - STAGE 4 (database integrity check)
Verified cause: The full integrity report is printed in the window and in
  startup.log. A real database problem reports sqlite errors such as
  "file is not a database"; the report names the database that failed.
Verified fix: Run START_DIAGNOSTIC.bat. It runs PRAGMA integrity_check on
  every database READ-ONLY (it cannot create or change anything) and says
  "ok" per database. If one database does not report ok, stop there: do not
  delete it and do not re-run setup over it. Report startup.log plus
  diagnostic.log. There is no verified automatic repair; anything else would
  be guessing with your data.
Source: ISSUE-036; ISSUE-037 (START_DIAGNOSTIC read-only contract)

SYMPTOM: Port 8788 (or 5173) is held by an application that is NOT Hero1, rc=20
Verified cause: Another program - often a leftover dev server - is already
  listening on the port. Hero1 verifies instance identity before reusing a
  port and never kills a foreign process.
Verified fix: Close the other application, then run START.bat again. The
  port checker reports rc=0 free, rc=10 verified Hero1 (it will be reused),
  rc=20 foreign (refused). To check by hand:
  .venv\Scripts\python.exe scripts\check_port.py 8788
  .venv\Scripts\python.exe scripts\check_port.py --frontend 5173
Source: ISSUE-025; ISSUE-028; ISSUE-029

Verified cause: A page answering on 5173 only proves the frontend server is
  up. The frontend reaches the API through a proxy to the backend on 8788;
  stage 9 verifies that whole path including backend identity.
Verified fix: Look at the "HERO1 Backend :8788" window - if it shows an

  8788 does not answer at all, the backend is down; close the service
  windows and run START.bat again so everything starts in order.

SYMPTOM: Validate answers NEEDS_METADATA / the UI shows SPEC_NEEDS_METADATA
Verified cause: There is no broker metadata snapshot stored for that exact
  instrument on that exact broker and server, so pip size, tick size,
  volume limits and stops distance are unknown. Hero1 never guesses these
  values and never marks such a strategy VALID - by design, not a bug.
Verified fix: On the Windows machine, open the MT5 terminal, log in to the
  broker/server, then use Metadata -> Refresh for that instrument; or
  Import a metadata snapshot that was exported from that broker/server.
  Validate again afterwards - it turns VALID only with a real snapshot.
  Metadata is kept separate per broker and per server; one broker's
  snapshot is never applied to another.
Source: tests/test_metadata_mt5.py; services/api metadata + spec validate

SYMPTOM: Metadata Refresh answers MT5 unavailable (503 MT5_UNAVAILABLE)
Verified cause: The MetaTrader 5 terminal / Python bridge is not available
  on this machine (for example the Linux development box, or MT5 not
  installed or not running). This is an honest refusal, not a crash, and
  no data was simulated in place of the real terminal.
Verified fix: Run Hero1 on the Windows machine with the MT5 terminal
  installed, open and logged in, and Refresh there. Alternatively Import a
  snapshot that was collected on such a machine. Strategies simply stay

Source: tests/test_metadata_mt5.py (Linux-unavailable paths); ISSUE register
  rule "MT5 is never simulated as real"

SYMPTOM: Volume or price rounding is refused for an instrument
Verified cause: Sizing uses the broker snapshot (digits, tick size, volume
  min/max/step). A pip is NOT always 10 points: it is 10 points only for
  3- and 5-digit symbols, otherwise one point. If the snapshot has missing
  or invalid tick geometry (for example a zero volume step), the adapter
  refuses to produce a number at all rather than invent one.
Verified fix: Refresh the metadata snapshot for that instrument on that
  broker/server (see the NEEDS_METADATA entry) and retry. Do not type pip
  or tick values in by hand.
Source: packages/mt5_adapter sizing rules; tests/test_metadata_mt5.py

SYMPTOM: import_market_data.py reports a dataset REJECTED (exit code 1)
Verified cause: At least one candle row failed validation; the exact
  reason is printed per line (HIGH below LOW, a non-numeric field, an
  unparseable date, or conflicting candles for the same timestamp). The
  import is all-or-nothing: zero candles were written, and the attempt is
  recorded as REJECTED in import_manifest.json for provenance.
Verified fix: Fix the export at the source - re-export the file from the
  MT History Center and import the fresh file. Exact duplicate rows are
  collapsed automatically and counted; CONFLICTING duplicates mean the
  export itself is ambiguous, so only a re-export resolves it. Never edit
  prices in the CSV by hand to force a pass.
Source: scripts/import_market_data.py; tests/test_import_market_data.py

SYMPTOM: Imported history has gaps, or starts later than the MT chart shows
Verified cause: Two real effects, both reported by the importer: (1) the
  MT History Center exports at most about 100,000 rows per file - the
  importer prints this note - so M1/M5 files cannot reach back further;
  (2) weekends and market closures are genuine gaps. The importer reports
  gaps (count and largest) and never invents candles to fill them.
Verified fix: For older history, export an older date range in MT and
  import that file too; importing a newer export rolls the store forward
  and the report counts any rows it overwrote. Gaps caused by market
  closure are real data - there is nothing to repair.
Source: scripts/import_market_data.py (gaps_found, largest_gap_seconds,
  rows_overwritten_other_source); verified against all seven XAUUSD
  exports, 419013 candles

SYMPTOM: ISSUE-046 - FETCH DATA returns copy_rates_range returned None
  (last_error=(-2, 'Terminal: Invalid params'))
Verified cause: For timeframes with no stored baseline the old fetch built a
  backfill request starting at epoch 0 (1969/1970) spanning decades to a
  century depending on timeframe, and built boundaries by converting stored
  epochs through a broker-server offset. MT5 rejected those ranges with
  Invalid params; D1 alone accepted an all-history request and appended
  thousands of candles that were never part of the supplied baseline.
Verified fix: FETCH DATA now refuses a timeframe with no stored baseline
  ("import the supplied CSV history first"), starts from the latest valid
  stored candle with a two-candle overlap, and builds timezone-aware UTC
  datetimes directly from stored UTC epoch seconds. A None response is a
  FAILED timeframe with the requested UTC range and last_error shown; it
  modifies nothing.
Source: services/api/app/market_data_service.py _fetch_one();
  tests/test_mt5_windows_integration.py (no-baseline + invalid-timestamp
  tests, mocked); commit fbd4a45973bc86402919b38853e80bf8095e8261

SYMPTOM: ISSUE-047 - FETCH DATA shows impossible dates (2926-11-06,
  1970-01-01, 2926-98-29) and offset -28800s (measured from live tick)
Verified cause: Timestamp conventions were mixed: stored candles were naive
  broker-server epochs, request boundaries were shifted by a broker offset,
  and a "current offset" was measured from a live tick (raw -27496s snapped
  to -28800s) even though a tick is not a reliable historical-timezone source.
  Unit-mixed or malformed rate timestamps were also not range-validated
  before storage/display, so impossible years could be rendered.
Verified fix: One canonical convention everywhere: UTC epoch seconds in the
  database. CSV server wall time (IC Markets GMT+2/+3, US DST dates) is
  converted to UTC once at import; MT5 rate time is stored verbatim only
  after validate_timestamp() accepts it (1980..2100, whole seconds - 1970,
  2926 and millisecond magnitudes are rejected with the source value named).
  Fetch boundaries and completion use current UTC time; no tick-derived or
  broker offset is measured, rounded or applied in the fetch path.
Source: packages/market_data store validate_timestamp();
  packages/mt5_adapter server_time (import-boundary conversion only);
  tests/test_legacy_parity.py; tests/test_mt5_windows_integration.py; fbd4a45973bc86402919b38853e80bf8095e8261

ISSUE-049 - LMS dashboard shows candles but the Windows application shows zero
stored candles in every timeframe (permanent baseline storage / sync)
================================================================================
Exact symptom: On the owner's Windows PC every timeframe reported zero stored
candles while the LMS server dashboard displayed the full 419,013-candle
XAUUSD history.

CONFIRMED root cause (verified in code and configuration, 2026-11-07):
1. The LMS preview backend was launched with an EXTERNAL data root
   (HERO1_DATA_ROOT=/home/user/hero1-workspace-data), so the LMS canonical
   store lived OUTSIDE the project at
   /home/user/hero1-workspace-data/MARKET_DATA/market_data.db.
2. The Windows launcher (scripts/START_INTERNAL.bat, scripts/run_backend.cmd)
   resolves its canonical DATA root project-relatively to <project>\DATA
   (when HERO1_DATA_ROOT is unset), i.e. a DIFFERENT database file:
   [HERO1_PROJECT_ROOT]\DATA\MARKET_DATA\market_data.db.
3. The repository .gitignore excluded the ENTIRE DATA/ directory, and the
   seven supplied CSVs existed only as LMS uploads. A git clone/pull on
   Windows therefore delivered neither the CSVs nor any market-data database,
   so the Windows store was created empty. Same filename, different files -
   nothing was wrong with the Windows UI or the API.

Permanent fix:
- The seven original supplied CSVs now live permanently in the project at
  DATA/MARKET_DATA/IMPORTS/XAUUSD/ (original filenames and bytes; SHA-256
  verified identical to the user-supplied files) and are the ONLY tracked

  repository on main, so LMS and Windows checkouts carry identical baselines.
- scripts/import_market_data.py now defaults --data-root to the project DATA
  directory (relative to the repository root, never the CWD, never /tmp) and
  with no FILE arguments discovers DATA/MARKET_DATA/IMPORTS/<SYMBOL>/*.csv.
  Identical sources skip by SHA-256 before parsing (fast, idempotent).
- The API lifespan runs market_data_service.ensure_baseline() on every
  startup: any installation imports its permanent CSVs into ITS OWN canonical
  DATA/MARKET_DATA/market_data.db (append-preserving, conflicts rejected,
  never fatal to startup). START_INTERNAL stage 6 runs the same import
  visibly before backend startup and fails the stage if a file is REJECTED.
- START_DIAGNOSTIC.bat step 5b prints the canonical DB path, per-timeframe
  candle counts/UTC ranges, and the baseline CSVs found.
- The LMS installation was migrated to the project DATA directory
  (/home/user/hero1-trading-platform/DATA), its DB rebuilt from the repo CSVs
  (419,013 candles, integrity ok, byte-identical counts/ranges to the
  previous external store), and the redundant external market-data DB copy

timeframes must list candles; the dashboard Historical data panel must show
the same counts and the DB path [project]\DATA\MARKET_DATA\market_data.db.
If step 5b shows no CSVs, the checkout is stale: git pull (the CSVs are
tracked since this fix).

ISSUE-050 - FETCH DATA reports PARTIAL: "terminal history conflicts with
stored candles" and whole timeframes stay untouched
================================================================================
Exact symptom (Windows, 2026-11-07): FETCH DATA with scope ALL returns
PARTIAL. Several timeframes fail with "terminal history conflicts with stored
candles" at timestamps such as 2026-10-16 12:31:00 / 12:30:00 / 10:45:00 /
12:00:00, while others update. No new candles are saved for the failed
timeframes even though the terminal has newer history.

CONFIRMED causes (code-verified 2026-11-07; terminal-side candle values can
only be captured on Windows - see "evidence still required" below):
1. The cited conflict timestamps are EXACTLY each timeframe's latest stored
   candle (M1 2026-10-16 12:31, M5/M30 12:30, M15 10:45, H1 12:00 UTC) - i.e.
   the two-candle overlap the fetcher deliberately requests. Every fetch
   therefore re-examines the boundary candles first.
2. The old comparison (store.candle_equal) required ALL fields to match,
   including `spread` and `volume`. The supplied CSVs store VOL as exported
   (all-zero for XAUUSD) and the History-Center SPREAD; the terminal reports
   its own spread/real-volume for the same historical bar, so boundary
   candles conflicted even when prices were identical.
3. The old merge aborted the ENTIRE timeframe transaction on the first
   conflict (_Conflict), discarding every valid new candle with it.

Stored boundary candles (canonical DB, provenance = the permanent CSVs):
  M1  2026-10-16 12:31:00  O 4177.35 H 4179.79 L 4177.32 C 4179.59
      tickvol 286  vol 0.0  spread 10   (XAUUSD_M1.csv)
  M5  2026-10-16 12:30:00  O 4176.15 H 4180.43 L 4175.63 C 4180.24
      tickvol 930  vol 0.0  spread 5    (XAUUSD_M5.csv)
  M15 2026-10-16 10:45:00  O 4181.83 H 4182.47 L 4181.02 C 4181.71
      tickvol 536  vol 0.0  spread 5    (XAUUSD_M15.csv)
  H1  2026-10-16 12:00:00  O 4171.89 H 4180.43 L 4171.50 C 4176.62
      tickvol 13718 vol 0.0  spread 5   (XAUUSD_H1.csv)
These are the last candles of the CSV exports; a terminal may legitimately
hold a revised/final version of a candle that was still forming at export
time (category C below), or differ only in spread/volume (category B).

Fix (conflict policy, categories A-D):
- store.classify_overlap(): A exact duplicate (all fields) -> skip;
  B OHLC+tick_volume equal but volume/spread differ -> representation
  difference, skip and count separately; C/D price or tick-volume differs
  -> CONFLICT: the stored candle is preserved untouched, the difference is
  recorded (conflict_details with stored vs incoming per-field values in
  the fetch report AND in the datasets.validation_report audit row), and
  the remaining valid new candles still append in the same transaction.
- Timeframe status: UPDATED (appended, no conflicts), UP_TO_DATE,
  PARTIAL (conflicts isolated, with or without appends), FAILED (only for
  real failures). Overall COMPLETE/PARTIAL/FAILED follows the same rule.
- No force-overwrite exists. A verified revision-acceptance policy is a
  separate, future, owner-approved change; conflicts stay visible until
  then.

Evidence still required (Windows): run FETCH DATA once and return one
conflict_details block (or the LOG-tab trace for the operation id). That
shows the terminal's actual values next to the stored ones above and
settles B (representation) vs C (broker revision) per timeframe.

ISSUE-051 - LOG tab was a placeholder; fetch operations were not traceable
================================================================================
Symptom: The LOG tab showed a Phase-6 placeholder and FETCH DATA failures
could not be reconstructed (only a final error message).

Fix: the LOG tab now reads the persistent registry event store (the existing
DATA-backed logging architecture - no competing system). Every FETCH DATA
carries an operation id (client-generated FETCH-YYYYMMDD-HHMMSS-XXXXXX, or
server-generated) and the backend records lifecycle stages under it:
fetch_request_received (with the resolved canonical DB path),
mt5_connection_verified, latest_stored_candle_identified,
mt5_history_response_received, candle_validation_complete,
timeframe_fetch_complete / timeframe_fetch_failed (stage + exception), and
fetch_operation_completed. Frontend user actions (DATA tab open, fetch
click, scope/filter changes, node inspect) are logged through POST /events
with the same operation id. The LOG tab filters by severity, component,
operation id, instrument and free text (server-side search over message +
payload); filters are display-only and never delete history. Events survive
backend restarts (verified on Linux: a failed MT5_UNAVAILABLE fetch still
leaves its fetch_request_received event, searchable by operation id).

DATA tab (same issue): the historical market-data panel and the generated

================================================================================
ISSUE-052 - FETCH DATA appears stuck, other tabs return Internal Server
Error, LOG shows only a few INFO events (no stage, no exception)
================================================================================
Exact symptom (Windows, 2026-11-07, operation FETCH-20261107-090358-B7E4F1):
After clicking FETCH DATA in the new DATA tab the operation seemed stuck;
navigating away and back produced "Internal Server Error"; the LOG tab
showed ~12 mostly-INFO events with no processing stage or exception.

Investigation (the operation id was generated on the owner's Windows
machine; it does not exist in the LMS event store - searched and absent -
so the exact Windows exception was NOT captured by the old code. That
absence is itself one of the confirmed defects below.)

CONFIRMED defects (code-verified 2026-11-07):
1. One blocking request: the DATA tab awaited a single synchronous
   POST /fetch for the whole ALL-timeframe fetch. There was no operation
   state, no polling and no resume - if the terminal took minutes
   (copy_rates_range can block while MT5 synchronizes/downloads history)
   or the request was interrupted, the UI could only spin, and reopening
   DATA started from nothing (busy state lived only in the unmounted
   component). Duplicate fetches were possible.
2. No timeout anywhere on the MT5 history call: a terminal that never
   answers would hold the request forever.
3. Failures left almost no trace: FetchError exits (MT5 unavailable /
   login required / connect failed) were raised after a single
   fetch_request_received event; per-timeframe exceptions were converted
   to result rows without recording stack traces; unhandled 500s were
   logged only to the server console, never to the persistent event
   store the LOG tab reads. Hence "only INFO events".
4. LOG loading silently truncated: GET /events returned the OLDEST events
   (ascending, limit-capped) with no total and no pagination, so the
   newest diagnostics could be invisible, and there was no COPY ALL /
   SAVE TO TXT export.

POSSIBLE cause of the Windows 500s (unproven - the old code captured no
evidence): the blocked fetch thread plus per-event registry writes and
concurrent tab requests contending on the SQLite registry, or an
exception in a worker thread. After this fix, any recurrence is recorded
in the LOG tab as an ERROR event with the full stack trace (stage
UNHANDLED_EXCEPTION or TIMEFRAME_FETCH_FAILED), which will settle it.

Fix:
- Fetch is now a BACKGROUND OPERATION: POST /market-data/fetch/start
  returns the operation id immediately (state QUEUED/RUNNING/COMPLETED/
  PARTIAL/FAILED). One running operation per instrument - a duplicate
  start returns the existing operation. GET /fetch/operations/{id} and
  GET /fetch/operations (latest) let reopening DATA resume the same
  operation; the DATA tab polls status (700 ms) and refreshes
  availability only when the operation lands. Other tabs/APIs stay
  responsive while a fetch runs (verified live).
- Per-timeframe MT5 timeout (default 180 s, HERO1_FETCH_TF_TIMEOUT_S):
  the call runs on a worker; on timeout the timeframe fails loudly at
  stage MT5_HISTORY_REQUEST and no data is modified. (A native terminal
  call cannot be killed; the abandoned worker is daemonized and the
  operation still completes/fails cleanly.)
- Full lifecycle stages under the operation id: OPERATION_CREATED,
  BACKEND_REQUEST_RECEIVED, DATABASE_PATH_RESOLVED, MT5_CONNECTION_CHECK,
  STORED_BASELINE_READ, TIMEFRAME_FETCH_STARTED, MT5_HISTORY_REQUEST,
  MT5_HISTORY_RESPONSE, TIMESTAMP_VALIDATION, CANDLE_VALIDATION,
  DUPLICATE_CHECK, CONFLICT_CHECK, DATABASE_TRANSACTION_STARTED,
  DATABASE_COMMIT, POST_COMMIT_VERIFICATION, TIMEFRAME_COMPLETED,
  OPERATION_COMPLETED / OPERATION_FAILED / TIMEFRAME_FETCH_FAILED -
  failures carry exception type, message and full stack trace.
  Unhandled API exceptions are also published to the event store.
- LOG tab: server-side pagination (total + Load older), COPY ALL LOGS
  and SAVE LOGS TO TXT export the COMPLETE filtered dataset page by page
  (oldest-first plain text, full details/stack traces, UTF-8 file
  HERO1_LOGS_YYYY-MM-DD_HH-MM-SS.txt). Clearing filters never deletes.
- The synchronous POST /fetch remains for API compatibility.

Live Linux verification: an ALL-scope operation went RUNNING -> FAILED
(honest MT5_UNAVAILABLE on this host) with a 6-event trace; the events
API reported total=30 with paging; unrelated APIs answered throughout;
the canonical DB was byte-identical afterwards (419,013 candles,
integrity ok, zero duplicate timestamps).
