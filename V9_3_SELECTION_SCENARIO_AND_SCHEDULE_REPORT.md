# V9.3 — selection, scenario identity and shared schedules

## Shared selection and safe workflow

Both actual node tables provide SELECT ALL / DESELECT ALL and per-row checkboxes. Selection is a set of canonical IDs over the **complete filtered population**, not the visible100-row render page. The UI states selected/eligible counts and retained selections outside the current filter; actions apply only to the current scope. Refresh does not silently clear selections. Live-ineligible rows are excluded from select-all and disabled individually; server validation rechecks every requested canonical ID.

Deep selected work uses `/api/deeptest/batches`, a persisted SQLite queue with at most5,000 unique IDs/request and one orchestration worker per backend process. The existing historical executor remains single-worker. Per-node settings are included, duplicates use shared material-signature protection, and progress distinguishes completed, partial, reused, skipped, interrupted, cancelled and failed outcomes. Incomplete-history warnings are **not auto-accepted**: the batch explicitly skips them with a reason; use the existing node coverage confirmation and resubmit. There are no trading/live-executor imports in this queue.

Batch IDs and results survive backend restart. The UI remembers its current ID and provides **Find saved batches** for recent persisted jobs. Live owner PID detection prevents another process from falsely interrupting a running batch. A dead owner is INTERRUPTED; resume is explicit. Cancel only stops remaining queue/observation: it never cancels a shared historical run or touches live workers. Resume re-evaluates current data/settings through normal dedupe; previous completed/failed records remain visible. Per-node observation deadline is30min; a timeout retains the run ID rather than killing/replacing its execution. Cross-process deployments have one coordinator per process, not a distributed global concurrency scheduler; per-signature claims still prevent duplicate equivalent simulations.

**LIVE TEST SELECTED is review only.** `/live-testing/selection/validate` returns canonical identity, eligibility, current risk/trade-limit/config and assigned schedule, with `started:0` and `orders_submitted:0`. Each node still requires its existing explicit START and every original broker/schedule/risk/sizing/trade-limit check. Per-node STOP and STOP ALL remain untouched. Selection, star, opening/assigning schedules, fetch and disclosure never start trading.

## Stable material identity

The fingerprint binds canonical node and strategy genome, effective historical engine configuration, symbol/TF, actual normalized dataset fingerprint/version, selected duration/observed candle cohort (or exact explicit custom endpoints), normalized settings, frozen offsets and saved Deep schedule/Inspect rule content. Material engine semantic versions are included; release names and Git labels are not execution inputs. Display names, notes, assignment timestamps, provenance labels and request keys do not create duplicate scenarios. Numeric settings representations normalize consistently through validation.

A Python request lock plus reentrant filesystem lock and a SQLite UNIQUE signature claim serialize reuse/insert across threads and processes. Twenty-four equivalent concurrent thread requests and a real two-process test demonstrate a single scenario/claim and shared live owner. Valid terminal analytics is required on the production reuse path. Failed/interrupted/invalid results require explicit retry; unbounded `force_rerun` is refused. Old rows/duplicate history are never deleted. Existing older fingerprints are not rewritten or asserted equivalent just by a matching display name. The audited logical original has no Deep table, so no pre-existing duplicate relation can honestly be proven there; the private acceptance DB had no duplicate stored signatures.

At execution, dataset materialization occurs under the existing store lock. Changed data or material engine configuration since queueing fails closed with an explicit retry message rather than producing a result under an old signature. The actual historical run freezes saved schedule, effective offsets and rule content; later scenario/live edits do not rewrite it.

## Shared28-cell schedule contract

`daily_schedule`: version1, boundary convention `legacy-live-utc-v1`, timezone UTC by default (validated IANA optional), seven weekdays × four booleans ASIA/LONDON/NEWYORK/OVERLAPS. All28 values persist. Global-session and day-master states are derived from cells and stored with the normalized model; mixed is represented as null and rendered natively indeterminate. A global checkbox changes its whole seven-day column; a day master changes its whole four-cell row; a cell changes only itself.

Preserved UTC windows: Asia[00,08), London[07,16), NewYork[12,21). The separate OVERLAPS bucket is the exclusive union[07,08) and[12,16); the three other columns exclude overlap hours. Off-hours[21,24) are blocked only when this matrix is explicitly active. This is deliberately versioned and documented, not silently reinterpreted as the older exchange-local Inspect sessions. The IANA zone changes the weekday **per UTC timestamp**, including midnight crossings and DST; it does not shift these legacy UTC session windows. Source CSV broker wall-clock conversion happens once on import, not again at schedule evaluation.

Old records without a matrix retain legacy behavior. The opted-in matrix replaces ONLY old days/sessions predicates in both historical `bar_mask` and live `evaluate`; explicit enabled state, windows, regimes, signal conditions, timeframe, risk, trade limits and other gates remain. Existing advanced legacy window handling is unchanged; the new per-timestamp DST guarantee applies to the matrix weekday evaluator, not a rewrite of all legacy scheduling algorithms.

## Named custom scenarios and hydration

Deep SCENARIO and Live SCHEDULE expose the same `ScenarioAssignment`/`DailySchedule` editor, plus the same matrix in Inspect filters/save popup. Named NODE or GLOBAL scenarios persist normalized rules, all28 cells, derived masters, timezone, boundary version and Inspect day/session/per-day/date rules. Explicit application re-reads the backend assignment and hydrates every cell and material filter; it is not only a dropdown label change. The UI displays name, content version, active/preview state, unsaved edits and outdated-copy warning, with discard/reset.

Assignments store immutable rule snapshots/content versions, not a mutable pointer into another node's working settings. Other-process changes invalidate assignment cache using SQLite data_version/connection change state. Removal restores the original schedule without changing risk/arming. Manual named save uses compare-and-set against the previously assigned ID under the shared mutation lock; stale edits return409. Invalid/incomplete matrices and timezones are rejected, not filled in silently. Historical results are immutable.

## Target-specific schedule preview

The final review found that the older Deep editor preview delegated to the Live engine, which would now attach a Live filter assignment even when the Deep assignment differed. It is corrected to call the shared schedule evaluator directly with the actual historical Deep override/default plus **Deep** rules. It does not read Live enabled/configuration or today's Live trade/cooldown history. The new isolation test gives Live an all-blocked matrix and Deep an all-allowed matrix, confirms the Deep preview is allowed, then removes only Deep's assignment and verifies the historical default remains independent of Live. Existing Live configuration/assignment remain byte-for-byte unchanged. This also corrects the previous misleading "live schedule fallback" preview label: the actual historical request has no such fallback when no Deep override exists. Runtime trading gates still apply on the Live path; this historical preview never starts anything.
